* Plan: Dota 2 Counter-Pick — Auth & Authorization Demo
A .NET 8 learning/demo project implementing a Dota 2 counter-pick discussion platform
with JWT authentication, role/claims/resource-based authorization, OAuth integration,
rate limiting, and a Bootstrap 5 frontend.

| ASP.NET Core| 8.0.25 (Microsoft.AspNetCore.App 8.0.25)                        |

| DB          | SQLite via EF Core 8.0                                          |

Key design decisions:
- `Hero.Roles` is a comma-separated string (avoids a ManyToMany join table).
- `LikeCount` is denormalized on Comment for fast reads (no COUNT() query).
- UserId is stored as a plain string in Comment, CounterSuggestion, SuggestionLike, RefreshToken
  (no EF navigation/constraint to Identity tables — Identity tables are managed by Identity itself).
- CounterSuggestion has two FKs to Hero (HeroId + CounterHeroId) — a self-referencing pattern
  through two separate foreign keys.
- SuggestionLike name is misleading — it stores likes on *comments*, not on suggestions.

** Phase 2: AuthController — JWT Login/Register (completed)

- [X] POST /auth/login
  - UserManager.FindByNameAsync → CheckPasswordAsync
  - Logs warning on unknown user or wrong password (ILogger)
  - On success: GenerateTokenResponse → returns { accessToken, refreshToken, expiresAt }
  - Rate-limited: [EnableRateLimiting("LoginLimit")] → 5/min/IP

- [X] POST /auth/register
  - UserManager.CreateAsync with RegisterDto validation (username 3-50, email, password 6-100)
  - Logs errors on failure, logs info on success
  - Returns JWT immediately (auto-login on register)
  - Rate-limited: 5/min/IP

- [X] POST /auth/refresh
  - Lookup RefreshToken by token value
  - Guards: null check → 401, IsRevoked → theft detection (revoke ALL user tokens) → 401, Expired → 401
  - Mark old token as revoked, generate new pair, save new RefreshToken
  - If old token was revoked: revoke ALL tokens for that user (theft detection)

- [X] POST /auth/revoke
  - Find RefreshToken by value → mark IsRevoked = true
  - Idempotent: if token not found, still returns 200 OK

- [X] TokenService.GenerateAccessToken()
  - JwtSecurityToken with claims (NameIdentifier, Name, Email, roles)
  - expires: 15 minutes, signing: HmacSha256 with Jwt:Key
  - Issuer/Audience from config (defaults "CounterPick" / "CounterPickApi")

- [X] TokenService.GenerateRefreshToken()
  - 64 random bytes via RandomNumberGenerator.Create()
  - Base64-encoded string
  - No expiry at generation — expiry is stored in DB (7 days)

** Phase 6: Rate Limiting (completed)

- [X] builder.Services.AddRateLimiter() with two policies:
  - "SearchLimit" (HeroesController GET):
    - Anonymous: partition by RemoteIpAddress, 3 permits / 10 min window
    - Authenticated: partition by NameIdentifier claim, 100 permits / 1 min window
  - "LoginLimit" (AuthController POST /login + /register):
    - Partition by RemoteIpAddress, 5 permits / 1 min window
  - RejectionStatusCode = 429

- [X] SlidingWindowRateLimiterOptions with SegmentsPerWindow = 1
  - Effect: behaves as fixed window (permits reset fully at window boundary)
  - Not truly sliding — a burst at the end of a window carries over no permits

** Remaining Gaps

- [ ] OAuth token in URL fragment — redirect to login.html#access_token=... rather than
      server-side POST to opener window or session-based handshake. Tokens visible in
      browser address bar. Accepted as learning-project limitation.

- [ ] Rate limiter SegmentsPerWindow=1 — behaves as fixed window (resets fully at window
      boundary). Not truly sliding. Usability concern at scale.

- [ ] No duplicate-counter-suggestion guard — same user can suggest same hero pair
      multiple times. Would require unique index on (HeroId, CounterHeroId, SuggestedById)
      or application-level check.

- [ ] CommentsController GET loads ALL IdentityUser records into memory (ToListAsync)
      for UserId→UserName mapping. At scale, should use a SQL join instead.

- [ ] DTOs defined inline in controllers (AddCommentDto in CommentsController.cs,
      AddCounterDto in CounterSuggestionsController.cs, UpdateCommentDto in CommentController.cs)
      instead of in Core/DTOs/. Minor architectural inconsistency.

- [ ] No admin override for comment deletion — even admins cannot delete other users'
      comments via the current CommentOwnerHandler. Would need additional requirement
      or check for admin role.

- [ ] CounterSuggestion has no CreatedAt timestamp — unlike Comment, suggestions don't
      track when they were added.

- [ ] No input validation on comment/suggestion content (no [Required] or [MaxLength]
      on AddCommentDto.Content, AddCounterDto.Reason, etc.)

- [ ] No CSRF protection — JWT stored in localStorage is XSS-vulnerable (common SPA
      trade-off, but HTTP-only cookies + anti-forgery tokens would be more secure).

- [ ] CORS is AllowAnyOrigin/AllowAnyMethod/AllowAnyHeader — permissive for the demo
      but should be restricted for any real deployment.
