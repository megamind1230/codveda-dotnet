* DotaLane
:PROPERTIES:
:UPDATED: 2026-06-21
:END:

Pick your lane. See the matchup. Get advice.

A microservices-based Dota 2 lane analysis tool — only the first 10 minutes
of the laning phase, no teamfight noise, no cross-lane interference.

** Features
- Pick a lane (MID / SAFE / OFF)
- Select your hero and the enemy hero
- See side-by-side stat comparison with advantages highlighted (green/red)
- Get lane verdict: *STOMP* / *SURVIVE* / *AVOID* with reasoning and bullet points
- Only stat-based — no MMR, no hidden match data, just raw numbers
- Reload endpoint publishes RabbitMQ event to update consumers
- Consul service discovery for dynamic routing

** Microservices Architecture with .NET
Microservices means *splitting a large application into multiple small
services*, where each service has a specific responsibility and can be
developed, deployed, and scaled independently.

Instead of:

#+begin_src text

├── Users
├── Products
├── Orders
├── Payments
└── Notifications
#+end_src

You create them as services:

#+begin_src text
User Service
Product Service
Order Service
Payment Service
Notification Service
#+end_src

Each service is its own ASP.NET Core application.

** 7. Multi-Stage Docker Builds

A single Dockerfile can produce a smaller final image by using multiple
~FROM~ statements. Each ~FROM~ is a *stage*; earlier stages contain build
tools, later stages contain only what is needed to run.

#+begin_src dockerfile
# Stage 1 — build
FROM mcr.microsoft.com/dotnet/sdk:8.0 AS build
WORKDIR /src
COPY . .
RUN dotnet publish src/HeroService/...csproj -c Release -o /app/publish

# Stage 2 — runtime
FROM mcr.microsoft.com/dotnet/aspnet:8.0 AS runtime
WORKDIR /app
COPY --from=build /app/publish .
ENTRYPOINT ["dotnet", "HeroService.dll"]
#+end_src

Why multi-stage:

- The SDK image is ~1.5 GB; the ASP.NET runtime image is ~200 MB
- Only the published output (DLLs, config) is copied to the final image
- No compiler, NuGet cache, or source code in the production image
- ~COPY --from=build~ pulls files from an earlier stage by name

** 8. Docker Compose

Docker Compose lets you define and run multi-container applications with a
single ~docker compose up~ command.

#+begin_src yaml
services:
  consul:
    image: hashicorp/consul:latest
    ports:
      - "8500:8500"
    healthcheck:                      # ← Docker-level health check
      test: ["CMD", "consul", "info"]
      interval: 5s
      retries: 5

  hero-service:
    build:
      context: .
      dockerfile: src/HeroService/Dockerfile
    ports:
      - "5001:5001"
    environment:
      - CONSUL_HTTP_ADDR=http://consul:8500
    depends_on:
      consul:
        condition: service_healthy    # ← wait until Consul is healthy
    restart: unless-stopped           # ← auto-restart on crash
#+end_src

Key concepts:

- *services* — each container is a service with a name, image/build, ports
- *ports* — ~"host:container"~ mapping so services are reachable from the host
- *environment* — env vars injected into the container at runtime
- *depends_on* — ordering and optional ~condition~ (service_started, service_healthy)
- *healthcheck* — Docker pings the container periodically (avoid depends_on timeouts)
- *restart* — crash recovery policy (no, always, on-failure, unless-stopped)

Docker Compose creates a *default network* so containers can reach each
other by service name (e.g. hero-service can reach ~http://consul:8500~).

Commands:

#+begin_src sh
docker compose build     # build all images
docker compose up -d     # start all containers in background
docker compose down      # stop and remove containers
docker compose logs -f   # tail logs from all services
docker compose ps        # show status of all services
#+end_src

** 9. Kubernetes Resources

Kubernetes (K8s) orchestrates containers across a cluster. This project uses
several K8s resource types:

*** Deployment

A Deployment manages a set of identical Pods. It handles rolling updates,
scaling, and self-healing.

#+begin_src yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: hero-service
spec:
  replicas: 1
  selector:
    matchLabels:
      app: hero-service
  template:
    metadata:
      labels:
        app: hero-service
    spec:
      containers:
        - name: hero-service
          image: dotalane/hero-service:latest
          ports:
            - containerPort: 5001
          envFrom:
            - configMapRef:
                name: dotalane-config
          env:
            - name: ADVERTISE_HOST
              value: "hero-service"
          readinessProbe:
            httpGet:
              path: /healthz
              port: 5001
            initialDelaySeconds: 5
            periodSeconds: 10
          resources:
            requests:
              memory: "64Mi"
              cpu: "100m"
            limits:
              memory: "256Mi"
              cpu: "500m"
#+end_src

- *replicas* — how many pods to run (scale horizontally)
- *selector/labels* — match pods to the deployment
- *readinessProbe* — K8s checks /healthz before routing traffic to a pod
- *resources* — ~requests~ (guaranteed) vs ~limits~ (maximum allowed)

*** Service

A Service provides a stable network endpoint for a set of pods (which may
be recreated with new IPs).

ClusterIP (default) — internal-only, reachable within the cluster:

#+begin_src yaml
apiVersion: v1
kind: Service
metadata:
  name: hero-service
spec:
  selector:
    app: hero-service           # routes to pods with this label
  ports:
    - port: 5001                # what other services connect to
      targetPort: 5001          # what the pod listens on
#+end_src

NodePort — exposes the service externally via a static port on every node:

#+begin_src yaml
spec:
  type: NodePort
  ports:
    - port: 5000
      targetPort: 5000
      nodePort: 30000           # external port (30000-32767)
#+end_src

** 11. gRPC in ASP.NET Core

gRPC uses Protocol Buffers (protobuf) for serialization and HTTP/2 for
transport. It is faster than REST/JSON for internal service-to-service calls.

Define a service in a ~.proto~ file:

#+begin_src proto
syntax = "proto3";
package dotalane;

service AdviceService {
  rpc GetAdvice(AdviceRequest) returns (AdviceResponse);
}

message AdviceRequest {
  int32 your_hero_id = 1;
  int32 enemy_hero_id = 2;
  string lane = 3;
}

message AdviceResponse {
  string verdict = 1;       // stomp / survive / avoid
  string reason = 2;
  repeated string advantages = 3;
  repeated string disadvantages = 4;
}
#+end_src

The .proto file is compiled by the ~Protobuf~ SDK item in the .csproj:

#+begin_src xml
<Protobuf Include="Protos\*.proto" GrpcServices="Both" />
#+end_src

This generates:
- ~AdviceService.AdviceServiceBase~ — base class the server inherits
- ~AdviceService.AdviceServiceClient~ — typed client for callers

        AdviceRequest request, ServerCallContext context)
    {
        // ... logic ...
        return Task.FromResult(response);

// Registration:

** 12. Kestrel Multi-Protocol Hosting

Some services in this project listen on *two ports* — one for gRPC (HTTP/2)
and one for REST (HTTP/1.1). This is configured in Kestrel:

#+begin_src csharp
builder.WebHost.ConfigureKestrel(options =>
{
    options.Listen(IPAddress.Any, 5002,
        o => o.Protocols = HttpProtocols.Http2);      // gRPC
    options.Listen(IPAddress.Any, 5004,
        o => o.Protocols = HttpProtocols.Http1);      // REST
});
#+end_src

Why both?

- gRPC requires HTTP/2 (h2c without TLS in development)
- The API Gateway (Ocelot) uses HTTP/1.1 for REST proxying
- Health checks (/healthz) are simple HTTP/1.1 GET requests
- Having separate ports avoids protocol negotiation issues

Service port map for MatchupService:

| Port | Protocol | Purpose                    |
|------+----------+----------------------------|
| 5002 | HTTP/2   | gRPC (AdviceService calls) |
| 5004 | HTTP/1.1 | REST + health (Gateway)    |

** 13. IHttpClientFactory

Instead of creating ~new HttpClient()~ manually (which can cause socket
exhaustion), use ~IHttpClientFactory~:

#+begin_src csharp
// Registration
builder.Services.AddHttpClient("HeroService", client =>
{
    client.BaseAddress = new Uri(heroServiceUrl);
    client.Timeout = TimeSpan.FromSeconds(5);
});

// Usage (injected)
public class MatchupServiceImpl : MatchupService.MatchupServiceBase
{
    private readonly IHttpClientFactory _httpClientFactory;

    public MatchupServiceImpl(IHttpClientFactory httpClientFactory)
    {
        _httpClientFactory = httpClientFactory;
    }

    private async Task<HeroDto?> FetchHeroAsync(int id)
    {
        var client = _httpClientFactory.CreateClient("HeroService");
        return await client.GetFromJsonAsync<HeroDto>($"/api/heroes/{id}");
    }
}
#+end_src

Benefits:

- Connection pooling — reuses TCP connections instead of opening new ones
- DNS rotation — respects DNS TTL and re-resolves addresses
- Timeout handling — each named client has its own timeout config
- Resilience — easy to add retry policies with Polly later

#+begin_src csharp
// Program.cs — Frontend
var builder = WebAssemblyHostBuilder.CreateDefault(args);
builder.RootComponents.Add<App>("#app");          // mounts App component
builder.Services.AddScoped(sp => new HttpClient
{
    BaseAddress = new Uri("http://localhost:5000") // → API Gateway
});
builder.Services.AddScoped<ApiService>();
await builder.Build().RunAsync();
#+end_src

How it works in this project:

1. The Blazor app is published (dotnet publish → wwwroot/)
2. Nginx serves the static files (index.html, .dll assemblies, .wasm runtime)
3. The browser downloads and executes the .NET code
4. ~HttpClient~ calls go to the API Gateway (~http://localhost:5000~) from the browser
5. The Gateway proxies to backend services (HeroService, MatchupService)

Nginx config for Blazor:

#+begin_src nginx
server {
    listen 80;
    location / {
        root /usr/share/nginx/html;
        try_files $uri $uri/ /index.html =404;  # SPA fallback
    }
}
#+end_src

~try_files $uri $uri/ /index.html~ is essential for Blazor routing — without
it, navigating directly to a sub-page returns 404.

** 17. RabbitMQ Event Pattern

RabbitMQ enables asynchronous communication between services via a
publish/subscribe pattern:

*** Publisher (HeroService)
#+begin_src csharp
// POST /api/heroes/reload
// 1. Fetches all hero IDs from the database
// 2. Publishes a HeroStatsUpdated event to a topic exchange
channel.ExchangeDeclare("dotalane.hero", "topic");
channel.BasicPublish("dotalane.hero", "hero.updated", ...);
#+end_src

*** Consumer (MatchupService, AdviceService)
#+begin_src csharp
public class HeroEventConsumer : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        var connection = factory.CreateConnection();
        var channel = connection.CreateModel();
        channel.ExchangeDeclare("dotalane.hero", "topic");
        channel.QueueDeclare("matchup-service.hero-events", durable: true);
        channel.QueueBind("matchup-service.hero-events",
                          "dotalane.hero", "hero.updated");
        // ... consume events ...
    }
}
#+end_src

Key concepts:

- *Exchange* — routing hub ("dotalane.hero", type: topic)
- *Routing key* — "hero.updated" lets consumers filter messages
- *Queue* — durable queue per consumer (survives broker restarts)
- *Binding* — connects a queue to an exchange with a routing key pattern
- *Event* — lightweight message with event type, timestamp, and data
