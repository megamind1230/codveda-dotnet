* Reading Claims
You often see:

#+begin_src csharp

#+end_src

or

#+begin_src csharp

#+end_src

Many beginners memorize these lines without knowing what =User= actually is.


** What is =User=?
After authentication succeeds, ASP.NET Core creates a:

#+begin_src text
ClaimsPrincipal
#+end_src

and assigns it to:

#+begin_src csharp
HttpContext.User
#+end_src

which is exposed in controllers as:

#+begin_src csharp
User
#+end_src

Think of it as:

#+begin_src text
Current Logged-in User
#+end_src

with a bag of claims attached.

Example:

#+begin_src text
User
├── Name = Hassan
├── Email = hassan@example.com
├── Role = Admin
└── Department = IT
#+end_src


** Why read claims?
Suppose you have:

inside the JWT.
#+begin_src json
{
  "sub": "123",
  "name": "Hassan",
  "email": "hassan@example.com"
}
#+end_src


You may want to:

- know who is making the request
- save who created a record
- show the user's name
- filter data by user

Example:
This lets users see only their own orders.

#+begin_src csharp
var userId =
    User.FindFirst(ClaimTypes.NameIdentifier)?.Value;
#+end_src

Then:

#+begin_src csharp
var orders =
    db.Orders
      .Where(o => o.UserId == userId);
#+end_src



** Why not trust the client?
Bad:

#+begin_src csharp
POST /orders
{
    "userId": "123"
}
#+end_src

The user can change:

#+begin_src json
{
    "userId": "999"
}
#+end_src

and access another user's data.

Instead:

#+begin_src csharp
var userId =
    User.FindFirst(ClaimTypes.NameIdentifier)?.Value;
#+end_src

Now the identity comes from the validated JWT, not from user input.

That's one of the biggest real-world uses of claims.

* Store Secrets Securely
This is one of the most important security topics.


** The beginner mistake
#+begin_src csharp
builder.Services
    .AddJwtBearer(options =>
    {
        options.TokenValidationParameters =
            new TokenValidationParameters
            {
                IssuerSigningKey =
                    new SymmetricSecurityKey(
                        Encoding.UTF8.GetBytes(
                            "super-secret-key"))
            };
    });
#+end_src

Or:

#+begin_src csharp
string password =
    "MyDatabasePassword123";
#+end_src

inside source code.

Very bad.


** Why is it bad?
Source code often ends up in:

- Git repositories
- backups
- CI/CD logs
- developer machines

If someone gets the secret:

#+begin_src text
They can impersonate users
Sign fake JWTs
Access databases
Call paid APIs
#+end_src


** Better approach
Use configuration.

Example:

#+begin_src json
{
  "Jwt": {
    "Key": "..."
  }
}
#+end_src

Read it:

#+begin_src csharp
builder.Configuration["Jwt:Key"];
#+end_src


** Better still: environment variables
Linux:

#+begin_src sh
export JWT_KEY="super-secret-value"
#+end_src

ASP.NET:

#+begin_src csharp
builder.Configuration["JWT_KEY"]
#+end_src

Now the secret is not stored in Git.


** Best for production
Use secret-management services:

- Microsoft Azure Key Vault
- Amazon Web Services Secrets Manager
- Google Cloud Secret Manager

Applications retrieve secrets securely at runtime.


** How do you store JWT signing keys or database passwords?

A strong answer is:

#+begin_src text
Never hardcode secrets in source code.

For development, use ASP.NET Core Secret Manager or environment variables.

For production, use a dedicated secret store such as Azure Key Vault, AWS Secrets Manager, or Google Secret Manager.
#+end_src
