* Task 1: Microservices Architecture with .NET
Microservices means *splitting a large application into multiple small
services*, where each service has a specific responsibility and can be
developed, deployed, and scaled independently.

Instead of:

#+begin_src text
Monolithic Application
├── Users
├── Products
├── Orders
├── Payments
└── Notifications
#+end_src

You create them as services:

#+begin_src text
User Service
Product Service
Order Service
Payment Service
Notification Service
#+end_src

Each service is its own ASP.NET Core application.


* 1. Design Microservices-Based Architecture
** Monolith vs Microservices
*** Monolith
#+begin_src text
Client
  |
  V
Single ASP.NET App
  |
  +-- Users
  +-- Orders
  +-- Payments
#+end_src

Pros:

- Easy to start
- Simple deployment

Cons:

- Hard to scale parts independently
- Large codebase becomes difficult to maintain


*** Microservices
#+begin_src text
Client
  |
  V
=API Gateway=
  |
  +-- User Service
  +-- Order Service
  +-- Payment Service
#+end_src

Pros:

- Independent deployment
- Independent scaling
- Teams can work separately

Cons:

- More complexity
- Networking issues
- Distributed debugging


** Example E-Commerce System
#+begin_src text
User Service
    |
Order Service
    |
Payment Service
    |
Notification Service
#+end_src

Responsibilities:

*** User Service
#+begin_src text
Register
Login
Profile
JWT
#+end_src

*** Product Service
#+begin_src text
Products
Categories
Inventory
#+end_src

*** Order Service
#+begin_src text
Create Orders

#+end_src

*** Payment Service
#+begin_src text
Process Payments
#+end_src

*** Notification Service
#+begin_src text
Emails

#+end_src

Each service owns its database:

#+begin_src text

#+end_src

This is an important microservice principle:
#+begin_quote
Database per service.
#+end_quote


* 2. API Gateway
Without a gateway:

#+begin_src text
Frontend
 |
 +--> User Service
 |
 +--> Product Service
 |
 +--> Order Service
#+end_src

Frontend must know every service.


With API Gateway:

#+begin_src text
Frontend
    |
    V
API Gateway
    |
    +--> User Service
    +--> Product Service
    +--> Order Service
#+end_src

Benefits:

- Single entry point
- Authentication
- Routing
- Rate limiting
- Logging


** Popular .NET Gateway
Ocelot

Example:

#+begin_src text
/api/users
/api/orders
/api/products
#+end_src

Gateway routes requests to correct services.


* 3. Service Discovery
Problem:

#+begin_src text
Order Service
needs
Payment Service
#+end_src

But Payment Service IP changes constantly.

Bad:

#+begin_src text
http://192.168.1.44
#+end_src


Service Discovery solves this.

Instead:

#+begin_src text
http://payment-service
#+end_src

A registry tracks service locations.


Popular tools:

- Consul
- Eureka
- Kubernetes built-in service discovery


Example:

#+begin_src text
Order Service
    |
    | asks registry
    V
Payment Service = 10.1.1.7
#+end_src


* 4. Inter-Service Communication
Microservices need to talk to each other.

Two common approaches:

** A. Synchronous Communication (gRPC)
#+begin_src text
Order Service
      |
      V
Payment Service
#+end_src

Request waits for response.


*** gRPC
Uses:

#+begin_src text
Protocol Buffers
HTTP/2
#+end_src

Advantages:

- Very fast
- Smaller payloads
- Strong typing

Example:

#+begin_src proto
service PaymentService {
  rpc ProcessPayment(PaymentRequest)
      returns (PaymentResponse);
}
#+end_src

ASP.NET Core supports gRPC natively.


*** When to use gRPC
When immediate response is needed.
#+begin_src text
Inventory Check
Payment Verification
User Validation
#+end_src



** B. Asynchronous Communication (RabbitMQ)
Instead of calling directly:

#+begin_src text
Order Service
     |
Publish Event
     |
RabbitMQ
     |
Notification Service
#+end_src


Example:

#+begin_src text
Order Created
#+end_src

Event is sent.

Consumers react later.

#+begin_src text
Send Email
Generate Invoice
Update Analytics
#+end_src


Advantages:

- Loose coupling
- Better scalability
- Services can be offline temporarily


Popular Broker: RabbitMQ

Workflow:

#+begin_src text
Order Service
      |
      V
RabbitMQ
      |
      +--> Notification Service
      |
      +--> Analytics Service
#+end_src


* gRPC vs RabbitMQ
| Feature            | gRPC      | RabbitMQ |
|--------------------+-----------+----------|
| Immediate response | Yes       | No       |
| Fast communication | Yes       | Good     |
| Event-driven       | No        | Yes      |
| Loose coupling     | Medium    | High     |
| Real-time request  | Excellent | Poor     |

Use:

#+begin_src text
Need response now?
    -> gRPC

Just notify others?
    -> RabbitMQ
#+end_src


* 5. Docker
Each service gets its own container.

#+begin_src text
User Service Container
Product Service Container
Order Service Container
#+end_src

Example Dockerfile:

#+begin_src dockerfile
FROM mcr.microsoft.com/dotnet/aspnet:8.0

COPY publish/ .

ENTRYPOINT ["dotnet", "UserService.dll"]
#+end_src

Build:

#+begin_src sh
docker build -t userservice .
#+end_src

Run:

#+begin_src sh
docker run -p 5001:8080 userservice
#+end_src


* 6. Kubernetes
Docker runs containers.

Kubernetes manages many containers.


Without Kubernetes:

#+begin_src text
Container crashes
=> manual restart
#+end_src

With Kubernetes:

#+begin_src text
Container crashes
=> auto restart
#+end_src


Features:

*** Scaling
#+begin_src sh
kubectl scale deployment userservice --replicas=5
#+end_src

#+begin_src text
User Service
 ├─ Instance 1
 ├─ Instance 2
 ├─ Instance 3
 ├─ Instance 4
 └─ Instance 5
#+end_src


*** Load Balancing
#+begin_src text
Request
   |
   +--> Pod1
   +--> Pod2
   +--> Pod3
#+end_src


*** Self-Healing
#+begin_src text
Pod dies
   |
   V
Kubernetes creates new Pod
#+end_src
