* Bugs and Fixes

** Bug 1 – File size read from stale path after move

   File: ~FileOrganizer.Core/Services/FileMover.cs~
   Lines: 100-105

   After ~File.Move(filePath, destPath)~ succeeds, the source path no
   longer exists.  The next line does:

   #+BEGIN_SRC csharp
   totalSize += new FileInfo(filePath).Length;
   #+END_SRC

   This throws ~FileNotFoundException~, which is caught as ~[SKIP]~,
   producing a misleading error for a file that was actually moved.
   ~totalMoved~ is already incremented by this point, so the return
   tuple is also wrong.

   *Fix:* capture the size *before* the move:

   #+BEGIN_SRC csharp
   var size = new FileInfo(filePath).Length;
   File.Move(filePath, destPath);
   totalMoved++;
   totalSize += size;
   #+END_SRC

** Bug 2 – Scan crashes on inaccessible files

   File: ~FileOrganizer.Core/Services/FileScanner.cs~
   Lines: 11-20

   ~Directory.EnumerateFiles()~ and the ~FileInfo~ constructor throw
   ~UnauthorizedAccessException~ / ~PathTooLongException~ with no
   handler.  A single unreadable file aborts the whole scan.

   *Fix:* wrap the per-file body in a try/catch and skip gracefully:

   #+BEGIN_SRC csharp
   foreach (var filePath in Directory.EnumerateFiles(directoryPath))
   {
       try
       {
           var fileInfo = new FileInfo(filePath);
           entries.Add(new FileEntry { ... });
       }
       catch (Exception ex)
           when (ex is UnauthorizedAccessException
                 or PathTooLongException)
       {
           Console.WriteLine($"[SKIP] {filePath} — {ex.Message}");
       }
   }
   #+END_SRC

** Bug 3 – Invalid regex crashes CLI and GUI

   Files:
   - ~FileOrganizer.Core/Services/NamedPatternResolver.cs~ (line 27)
   - ~FileOrganizer.Core/FileOrganizer.cs~ (line 44)
   - ~FileOrganizer.Gui/ViewModels/MainWindowViewModel.cs~ (line 179)

   When ~UseRegex=true~ and the user types an invalid pattern
   (e.g. ~[unclosed~), ~Regex.IsMatch()~ throws
   ~RegexParseException~ (~ArgumentException~).  No caller catches it.

   *Fix (option A – validate upfront):* wrap the ~Match()~ call in a
   try/catch in every caller.

   *Fix (option B – resilient resolver):* catch inside the loop in
   ~NamedPatternResolver.Match()~ and ~continue~ to the next pattern:

   #+BEGIN_SRC csharp
   try
   {
       if (Regex.IsMatch(file.FileName, pattern, options))
       { ... }
   }
   catch (ArgumentException) { continue; }
   #+END_SRC

** Bug 4 – Except() uses reference equality

   Files:
   - ~FileOrganizer.Core/FileOrganizer.cs~ (line 45)
   - ~FileOrganizer.Gui/ViewModels/MainWindowViewModel.cs~ (line 323)

   ~FileEntry~ is a class without ~Equals~ / ~GetHashCode~ overrides,
   so ~Enumerable.Except()~ uses reference identity.  This works today
   only because ~NamedPatternResolver.Match()~ returns references from
   the same input list.  If entries were ever cloned, files would be
   double-processed.

   *Fix:* add value-based equality to ~FileEntry~:

   #+BEGIN_SRC csharp
   // FileOrganizer.Core/Models/FileEntry.cs
   public override bool Equals(object? obj) =>
       obj is FileEntry other && SourcePath == other.SourcePath;

   public override int GetHashCode() =>
       SourcePath.GetHashCode();
   #+END_SRC

** Bug 5 – Browse button bypasses ViewModel binding

   File: ~FileOrganizer.Gui/Views/MainWindow.axaml.cs~
   Line: 30

   ~SourceDirTextBox.Text = path~ sets the control directly instead of
   the ViewModel property.  If the TwoWay binding hasn't initialised
   yet, the ViewModel never learns about the directory and the preview
   stays empty.

   *Fix:* set the ViewModel property instead:

   #+BEGIN_SRC csharp
   if (path != null && DataContext is ViewModels.MainWindowViewModel vm)
       vm.SourceDirectory = path;
   #+END_SRC
