* Bugs and Fixes

** Bug 1 – File size read from stale path after move                                  [FIXED]

   File: ~FileOrganizer.Core/Services/FileMover.cs~
   Lines: 100-105

   After ~File.Move(filePath, destPath)~ succeeds, the source path no
   longer exists.  The next line does:

   #+BEGIN_SRC csharp
   totalSize += new FileInfo(filePath).Length;
   #+END_SRC

   This throws ~FileNotFoundException~, which is caught as ~[SKIP]~,
   producing a misleading error for a file that was actually moved.
   ~totalMoved~ is already incremented by this point, so the return
   tuple is also wrong.

   *Fix (applied):* capture the size *before* the move:

   #+BEGIN_SRC csharp
   var size = new FileInfo(filePath).Length;
   File.Move(filePath, destPath);
   totalMoved++;
   totalSize += size;
   #+END_SRC

   Verified fixed in current ~FileMover.Unorganize()~ (line 102 captures ~size~
   before ~File.Move~ at line 110) and ~FileMover.Move()~ (line 52 uses
   ~entry.SizeBytes~ captured at scan time).

** Bug 2 – Scan crashes on inaccessible files                                          [FIXED]

   File: ~FileOrganizer.Core/Services/FileScanner.cs~
   Lines: 11-20

   ~Directory.EnumerateFiles()~ and the ~FileInfo~ constructor throw
   ~UnauthorizedAccessException~ / ~PathTooLongException~ with no
   handler.  A single unreadable file aborts the whole scan.

   *Fix (applied):* wrap the per-file body in a try/catch and skip gracefully:

   #+BEGIN_SRC csharp
   foreach (var filePath in Directory.EnumerateFiles(directoryPath))
   {
       try
       {
           var fileInfo = new FileInfo(filePath);
           entries.Add(new FileEntry { ... });
       }
       catch (Exception ex)
           when (ex is UnauthorizedAccessException
                 or PathTooLongException)
       {
           _logger.Warning(ex, "Skipping inaccessible file: {FilePath}", filePath);
       }
   }
   #+END_SRC

   Verified fixed in current ~FileScanner.Scan()~ (line 32).

** Bug 4 – Except() uses reference equality                                             [FIXED]

   Files:
   - ~FileOrganizer.Core/FileOrganizer.cs~ (line 58)
   - ~FileOrganizer.Gui/ViewModels/MainWindowViewModel.cs~ (line 394)

   ~FileEntry~ is a class without ~Equals~ / ~GetHashCode~ overrides,
   so ~Enumerable.Except()~ uses reference identity.  This works today
   only because ~NamedPatternResolver.Match()~ returns references from
   the same input list.  If entries were ever cloned, files would be
   double-processed.

   *Fix (applied):* add value-based equality to ~FileEntry~:

   #+BEGIN_SRC csharp
   // FileOrganizer.Core/Models/FileEntry.cs
   public override bool Equals(object? obj) =>
       obj is FileEntry other && SourcePath == other.SourcePath;

   public override int GetHashCode() =>
       SourcePath.GetHashCode();
   #+END_SRC

   Verified fixed in current ~FileEntry~ (line 13).

** Bug 6 – ReadLine.Read() may return null, crashing on .Trim()                        [UNFIXED]

   File: ~FileOrganizer.Cli/Program.cs~
   Lines: 63, 71

   If the user presses Ctrl+C / Ctrl+D at the interactive prompt,
   ~ReadLine.Read()~ may return ~null~.  The subsequent ~.Trim()~ call
   throws a ~NullReferenceException~ instead of handling graceful exit.

   #+BEGIN_SRC csharp
   sourceDir = ReadLine.Read("Enter source directory path: ").Trim();   // NRE if null
   #+END_SRC

   *Fix:* use null-conditional access + fallback:

   #+BEGIN_SRC csharp
   sourceDir = (ReadLine.Read("Enter source directory path: ") ?? "").Trim();
   if (string.IsNullOrEmpty(sourceDir)) return null;   // user cancelled
   #+END_SRC

** Bug 7 – Bash regex =~= fails silently on invalid patterns                          [UNFIXED]

   File: ~file-organizer~
   Line: 119-121

   When ~use_regex=1~ and the user enters an invalid regex pattern,
   bash's =~= operator prints an error to stderr but the branch acts as
   "no match".  The error is visible in the terminal but the script
   does not handle it, potentially confusing users.

   #+BEGIN_SRC bash
   if [[ "$name" =~ $pat ]]; then   # bash error if $pat is invalid
       ...
   fi
   #+END_SRC

   *Fix:* suppress stderr and validate the regex upfront with a helper:

   #+BEGIN_SRC bash
   if [[ "$name" =~ $pat ]] 2>/dev/null; then   # suppress REGEX error
       ...
   fi

   # Or validate the pattern first:
   if echo "" | grep -P "$pat" &>/dev/null; then
       # valid
   else
       warn "Invalid regex: $pat"
   fi
   #+END_SRC

** Bug 8 – Container pattern tags starting with =.= create hidden folders              [DOCUMENTED]

   File: ~file-organizer~ (bash) and ~FileOrganizer.Core/Services/NamedPatternResolver.cs~ (C#)

   When regex patterns match a value starting with =.= (e.g.
   =--patterns ".*\.tmp" --regex=), the folder name becomes =.tmp=
   which is hidden in most file managers.

   This is not a code bug but an ergonomic footgun.  The =SanitizeFolderName=
   method in C# strips invalid path chars but does not strip leading dots.
   The bash version uses =sanitize()= which only replaces =/=.

   *Mitigation:* add a check to prepend =_= if the sanitised name starts with =.=:

   #+BEGIN_SRC csharp
   // NamedPatternResolver.cs
   private static string SanitizeFolderName(string name)
   {
       foreach (var c in Path.GetInvalidFileNameChars())
           name = name.Replace(c, '_');
       if (name.StartsWith('.'))
           name = "_" + name;   // avoid hidden folders
       return name;
   }
   #+END_SRC

   #+BEGIN_SRC bash
   # file-organizer — sanitize()
   sanitize() {
       local name="$1"
       name="${name//\//_}"
       [[ "$name" == .* ]] && name="_$name"
       echo "$name"
   }
   #+END_SRC
